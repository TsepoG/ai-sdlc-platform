# Phase 02 — Persistence and workflow

**Goal:** an Initiative can be created and walked through the Brief stage —
draft, submit, changes requested, resubmit, approve — against a real
PostgreSQL database, with immutable versions, hash-bound decisions and a
verifiable audit trail. The Phase 01 rules decide every transition; this phase
stores the results and runs them in transactions.

**Branch:** `feat/phase-02-persistence-and-workflow` · **Size:** about 2 weeks.

**Read first:** `docs/design/core-design.md` §5–§6 and §8,
`CODING_PRINCIPLES.md` §10, and the Phase 01 code in `src/stages` and
`src/workflow`.

## Decision: no separate workflow engine for the MVP

Workflow state lives in PostgreSQL. A long wait for an approval is a row, not
a running process. The pure rules from Phase 01 (`nextMove`, hashing, decision
rights) decide every transition inside a database transaction. Background work
(outbox writes now, agent runs from Phase 03) goes through a small job worker
in the same service. A durable engine (Step Functions or Temporal) is
reconsidered at the Build slice, when GitHub Actions steps and SLA timers
arrive. Record this as **ADR 0004** and update `docs/design/core-design.md`
(§5 implementation note, §11 stack, §13 open questions) to match.

## In scope

### 1. Infrastructure (`infra/`)

- **RDS for PostgreSQL** in the platform stack: smallest Graviton class
  (e.g. `db.t4g.micro`), single-AZ in dev, multi-AZ in prod, private isolated
  subnets, storage encrypted, 7-day automated backups, deletion protection and
  snapshot-on-delete in prod only. Use a current major version that RDS offers
  in `af-south-1`; check, don't assume.
- **Credentials** generated by CDK into Secrets Manager; the service reads them
  as ECS secrets (fields, not the whole JSON). No password in code, config or
  logs.
- **S3 artifact bucket:** block all public access, encryption, versioning,
  enforce TLS, no website hosting. Retain in prod, destroy-with-objects in dev.
- **Network:** a security group rule from the service to the database on 5432
  only.
- **IAM:** the task role can read/write the artifact bucket and read the DB
  secret — nothing broader.
- **Health:** keep the ALB health check on `/health` (liveness). Add `/ready`,
  which checks the database.
- CDK assertion tests for all of the above, including "not publicly
  accessible", encryption, and the prod-only protections.

### 2. Database schema and migrations (`migrations/`, `src/db/`)

- Plain SQL migrations, numbered (`0001_*.sql` …), applied by a small runner in
  `src/db` with a `schema_migrations` table and a PostgreSQL **advisory lock**
  so two tasks starting together can't both migrate. The service runs pending
  migrations at startup before it listens. No ORM.
- Tables per `core-design.md` §6: `initiatives`, `stage_runs`, `step_runs`,
  `artifacts`, `artifact_versions`, `review_packages` (+ a join table for its
  versions), `gate_runs`, `decisions`, `open_questions`, `comments`,
  `agent_runs`, `jobs` (outbox and background work), `external_links`,
  `audit_events`. Users are text IDs for now; roles arrive with SSO in
  Phase 04.
- **Enforced in the database, not just in code:**
  - `artifact_versions`, `decisions` and `audit_events` are insert-only
    (triggers reject UPDATE and DELETE).
  - Foreign keys and CHECK constraints for every enum-like column (states,
    outcomes, step types).
  - Unique constraints that make retries safe: one open package per stage
    run, one decision per gate run, unique job idempotency keys, unique
    version numbers per artifact.
- `src/db` (public `index.js`): connection pool from config, `withTransaction`
  helper, migration runner. Uses `pg`.

### 3. Content store (`src/content/`)

- `ContentStore` contract: `put(content) → { key, hash }`, `get(key)`.
  Keys are content-addressed (`sha256/<hash>`), so storing the same content
  twice is a no-op.
- Implementations: S3 (via `@aws-sdk/client-s3`) and local filesystem (for
  local runs and tests). Chosen by config.
- The S3 implementation is unit-tested with a test double — no AWS calls.

### 4. Workflow services (`src/initiatives/` or similar; name it in the plan)

Application services that load state, call the Phase 01 rules, and write the
result in **one transaction** with its audit event(s):

- `createInitiative({ title, request, notes }, actor)` — Initiative, Brief
  stage run (attempt 1), its step runs, and the inputs stored as user-created
  versions.
- `saveVersion(artifactId, content, actor)` — new immutable version with
  content hash and `sourceVersionIds`.
- `submitPackage(stageRunId, versionIds, actor)` — refuses if any blocking
  open question is unanswered; supersedes any open package; completes the
  drafting work step; opens the first gate (gate run with `dueAt` from
  `slaHours`).
- `decide(gateRunId, { outcome, packageHash, reworkTarget, feedback }, actor,
  roles)` — `assertCurrentPackage` (409 on stale), `assertCanDecide`
  (403), then maps the decision to a Phase 01 outcome and applies `nextMove`:
  - approve → next step, or stage approved;
  - request changes → package closed, steps restart at the first;
  - reject with target → new stage-run attempt at the target; later stage
    runs `superseded`;
  - reject without target → Initiative `cancelled`.
- **Stage handoff:** when a stage is approved, the next stage's run starts with
  the approved package as input **if that stage is enabled**; otherwise the
  Initiative becomes `awaiting_stage` with `currentStageKey` set to it.
- **Upstream changed:** when a stage is re-approved after rework, downstream
  stage runs that consumed older versions are flagged `upstream_changed` and
  blocked. Test this with a fixture stage directory where two stages are
  enabled (Brief is the only enabled stage in the real config).
- `addOpenQuestion`, `answerQuestion`, `addComment`.
- `getInitiative(id)` and `getTimeline(id)` (audit events in order).

### 5. Audit (`src/audit/`)

- `appendAuditEvent(tx, event)` — called by every service inside the same
  transaction. Each event stores `prevHash` and
  `hash = sha256(prevHash + canonical JSON of the event)`. Serialise
  appends (e.g. a lock on a chain-head row) so the chain can't fork.
- `verifyAuditChain()` — recomputes and reports the first break.

### 6. Job worker (`src/jobs/`)

- `jobs` table as the outbox: type, payload, idempotency key, status,
  attempts, `run_after`, last error.
- Worker loop claims jobs with `FOR UPDATE SKIP LOCKED`, runs the handler for
  the job type, retries with exponential backoff up to 5 attempts, then marks
  the job failed. Handlers must be idempotent.
- Phase 02 registers one handler: a `log` handler used by tests and to prove
  the loop. Real handlers (agent runs, MS Teams) come in Phases 03 and 05.
- Runs in the same service process; started and stopped with the server.

### 7. API (local and test only for now)

The dev load balancer is public HTTP with no SSO yet, so **workflow routes are
off in deployed environments**: they register only when config enables them,
and config refuses to enable them unless `PLATFORM_ENV` is `local` or `test`.

- `POST /initiatives`, `GET /initiatives/:id`, `GET /initiatives/:id/timeline`
- `POST /artifacts/:id/versions`, `GET /versions/:id`
- `POST /stage-runs/:id/packages`
- `POST /gate-runs/:id/decisions` (409 on stale hash, 403 on duties)
- `POST /open-questions/:id/answer`
- Identity for now: a dev-only header pair (user ID and roles), accepted only
  under the same local/test condition. Phase 04 replaces it with SSO.
- Request bodies validated with Zod; responses never include internal errors.

### 8. Config (`src/config`)

Add database settings (from discrete env vars, which ECS fills from the
secret), content store type and bucket, `WORKFLOW_API_ENABLED`,
`AUTH_MODE`, and worker settings. Update `.env.example`.

### 9. Local development and CI

- `docker-compose.yml` with PostgreSQL for local runs. README explains
  `docker compose up -d`, migrations, and running the API locally.
- Tests that need a database read `TEST_DATABASE_URL`; each test file gets
  an isolated schema or transaction rollback so tests don't interfere.
- CI runs PostgreSQL as a service container so database tests run on every
  PR and count toward coverage. Coverage stays ≥ 90%.
- The container job also checks `/ready` responds once the image is running
  against the CI database.

## Tests (beyond unit tests for each module)

- **End-to-end against PostgreSQL:** create → save version → submit →
  request changes → new version → resubmit → approve; Initiative ends
  `awaiting_stage` at `ux-design`; the timeline lists every step; the audit
  chain verifies.
- Stale package hash → 409 and nothing written. Package author approving →
  403 and nothing written. Blocking open question → submission refused.
- UPDATE or DELETE on `artifact_versions`, `decisions` or `audit_events` fails
  at the database.
- Tampering with one audit row makes `verifyAuditChain` report it.
- Rework and upstream-changed with the two-stage fixture config.
- Concurrent decisions on the same gate: exactly one wins.
- Job worker: success, retry with backoff, failure after 5 attempts,
  idempotency key prevents duplicates, two workers don't run the same job.
- Migrations: fresh database migrates; running again is a no-op; two
  concurrent runners don't both apply.
- Config refuses `WORKFLOW_API_ENABLED` or dev auth outside local/test.
- CDK assertions for RDS, S3, security groups and IAM.

## Out of scope

AI adapters and the agent run loop (Phase 03), SSO and the web app (Phase 04),
MS Teams and timeline UI (Phase 05), version diffs, comments UI, SLA
reminders, any write route exposed on the dev load balancer.
